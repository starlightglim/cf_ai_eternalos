# 12 — Orchestrator v2: Desktop-Aware App Generation

> How the OrchestratorAgent should create apps that **use the user's desktop data**
> (gallery apps that pull pictures, music players that read audio files, notes apps
> that read and write text, etc.).
>
> **Parent docs:** [01-apps-interop.md](01-apps-interop.md) (the platform spec),
> [ROADMAP.md](ROADMAP.md). This doc is the concrete next-iteration plan for the
> orchestrator and adjusts 01-apps-interop.md where better primitives exist now.

## The gap we're closing

Today ([OrchestratorAgent.ts](../packages/worker/src/agents/OrchestratorAgent.ts),
[appTools.ts](../packages/worker/src/agents/tools/appTools.ts)):

- `buildAppFromPrompt` produces hermetic HTML/CSS/JS. The LLM is told literally
  "The app runtime is hermetic: no … desktop bridge, no file access."
- So when a user says "build a gallery app for my photos", the LLM ships a
  gallery that expects the user to paste URLs. It cannot see that the user has
  47 JPGs on their desktop with captions already generated.
- `fs.list` / `fs.read` endpoints exist ([apps.ts](../packages/worker/src/routes/apps.ts))
  but no app has ever been generated that uses them, and the `window.eternal.*`
  bridge promised in [01-apps-interop.md](01-apps-interop.md) isn't wired up.

The platform is ~70% built. This doc closes the loop: orchestrator → app
generator → runtime bridge → user data. "Build me a gallery" should result in an
app whose grid is populated with *my actual photos* the moment it opens.

## Goals

1. An app generated by a single "build me an X" message can read relevant
   desktop data on first launch — no follow-up permission dance except a single
   install dialog.
2. The orchestrator makes a smart, reversible decision about what data the
   app needs, declares those permissions, and surfaces them to the user.
3. The runtime bridge is small, legible, and works without a postMessage hop
   on the hot path.
4. Existing hermetic apps (calculator, todo) keep working unchanged.
5. The LLM can generate polished apps that feel native in one turn, not three.

## Non-goals (this milestone)

- Writing back to the desktop from apps (`fs.write`). Read-first; write lands in
  Phase B.
- Inter-app IPC, virtual folders, outbound network allowlists. Those are
  separate axes in [01-apps-interop.md](01-apps-interop.md) and can follow.
- A per-user app bazaar / install flow for third-party apps. The orchestrator
  only creates apps the user owns.
- Killing the regex router or switching models. We can iterate on both but they
  are not what's blocking desktop-aware apps.

## Prior art (what we learned)

- **Claude Artifacts.** One-shot self-contained HTML + optional `window.claude.complete(prompt)`
  for AI inside the artifact. Proves users expect "describe it → get a working
  thing" as the primitive. They don't want a plan-approve-build ceremony for
  small apps. ([support.claude.com](https://support.claude.com/en/articles/11649438-prototype-ai-powered-apps-with-claude-artifacts))
- **v0 composite model family.** Vercel routes "new generation / big change"
  through a frontier model and "small edit" through a fast Quick-Edit model.
  Relevant for us: `buildAppFromPrompt` and `updateApp` are two different jobs
  and should probably use different models. ([vercel.com](https://vercel.com/blog/v0-composite-model-family))
- **Bolt.new / StackBlitz WebContainers.** Full filesystem + terminal inside the
  browser. Great DX but a heavy dep. Wrong shape for us — Dynamic Workers give
  us better isolation cheaper. ([stackblitz-labs/bolt.diy](https://github.com/stackblitz-labs/bolt.diy))
- **MCP Apps.** Interactive HTML UIs returned from tool calls, rendered in
  iframes with `sandbox="allow-scripts allow-forms"` (no `allow-same-origin`),
  with a JSON-RPC postMessage protocol for host ↔ app calls. This is exactly
  the threat model we want, and confirms the sandbox flags. ([algora.io/claims/Zp7itqxoBXXxrBZB](https://algora.io/claims/Zp7itqxoBXXxrBZB))
- **Cloudflare Dynamic Workers, now GA'd with `ctx.props`.** The bit that
  changes our architecture: a Dynamic Worker can receive a *service binding*
  whose `props` are per-instance (e.g. `{ uid, appId, granted }`). This lets us
  call back from the sandboxed app into parent-controlled code without a
  postMessage bridge on the hot path. Zite (a chat-to-CRUD-app product) is in
  production on exactly this pattern. ([blog.cloudflare.com/dynamic-workers](https://blog.cloudflare.com/dynamic-workers/))

## Architecture

### Two-layer bridge

We keep the contract from [01-apps-interop.md](01-apps-interop.md) —
`window.eternal.fs.list()`, `window.eternal.fs.read(itemId)`, etc. — but we
back it with a faster path than cross-frame postMessage.

```
┌──────────────────────────────────────────────────────────────┐
│ Parent frame (eternalos.app)                                 │
│   iframe sandbox="allow-scripts"                             │
│   src = /api/apps/:appId/                                    │
└─────────────────────┬────────────────────────────────────────┘
                      │ HTTP (same origin as iframe's src)
                      ▼
┌──────────────────────────────────────────────────────────────┐
│ Worker (parent), route /api/apps/:appId/*                    │
│   LOADER.get(`app-${appId}@v${v}`, () => ({                  │
│     mainModule, modules,                                     │
│     globalOutbound: buildOutbound(granted.network),          │
│     bindings: {                                              │
│       ETERNAL: ctx.exports.EternalService({                  │
│         props: { uid, appId, granted }                       │
│       }),                                                    │
│     },                                                       │
│   })).getEntrypoint().fetch(request)                         │
└─────────────────────┬────────────────────────────────────────┘
                      │ request flows into the Dynamic Worker
                      ▼
┌──────────────────────────────────────────────────────────────┐
│ Dynamic Worker (the user's app)                              │
│   route /_eternal/fs/list → env.ETERNAL.list(...)            │
│   route /_eternal/fs/read/:id → env.ETERNAL.read(...)        │
│   everything else → the user's static assets (index.html…)   │
│                                                              │
│   runtime.js served alongside the app exposes                │
│     window.eternal = { fs: { list, read, readText, … }, … }  │
│   as a thin fetch wrapper over /_eternal/…                   │
└──────────────────────────────────────────────────────────────┘
                      │ RPC via service binding (not network)
                      ▼
┌──────────────────────────────────────────────────────────────┐
│ EternalService (WorkerEntrypoint exported by parent)         │
│   this.ctx.props = { uid, appId, granted }                   │
│   list(pathGlob) → checks granted.fs.read → UserDesktop DO   │
│   read(itemId)  → checks granted.fs.read → R2 blob           │
└──────────────────────────────────────────────────────────────┘
```

### Why service binding + `ctx.props` beats postMessage here

- **No cross-frame hops on the hot path.** `window.eternal.fs.list()` is one
  `fetch('/_eternal/fs/list')` to the app's own origin, handled inside the
  Dynamic Worker. Parent frame isn't involved per call.
- **No capability-token dance.** `granted` is bound into the Dynamic Worker at
  load time via `ctx.props`. The iframe never sees a token, can't leak one, and
  we don't have to mint + rotate 5-minute tokens per call. Revocation still
  works: bump the app's version when grants change, which forces a fresh worker
  load that picks up the new props.
- **Auditable surface.** The `EternalService` class is a single file in parent
  code. Every read goes through one method with `this.ctx.props.granted` as the
  policy. No "oh this fs.read went through the other endpoint" drift.
- **Sandbox preserved.** The Dynamic Worker still has `globalOutbound:
  buildOutbound(network)` and the iframe still has `sandbox="allow-scripts"`.
  `ctx.props` is a parent-provided capability, not a user-grantable one.

### Existing tokens keep working for the out-of-app case

The mint-capability-token endpoint at
[apps.ts:handleAppCapability](../packages/worker/src/routes/apps.ts) is still
useful for anything that talks to the app API *from outside the Dynamic Worker*
— e.g. an install dialog in the parent frame that wants to preview what an app
can see. We keep it; we just stop being the hot-path mechanism for in-app
fetches.

### Keep postMessage for things that must reach the parent

A few APIs genuinely need the parent frame:

- `window.eternal.window.setTitle()`, `close()`, `resize()` — parent owns the
  window chrome.
- `window.eternal.onIntent(...)` — launch-intent payloads (e.g. "open this
  item") pushed from parent when the app is spawned.

Those use a minimal postMessage channel. Everything data-ish goes through
`/_eternal/*`.

## The `window.eternal` surface (v1)

Matches [01-apps-interop.md §bridge API](01-apps-interop.md) but narrowed to
read-only + window controls for this milestone.

```ts
window.eternal = {
  appId: string;
  hostVersion: string;
  fs: {
    list(opts?: { path?: string; mimeType?: string; limit?: number }): Promise<Item[]>;
    read(itemId: string): Promise<Blob>;
    readText(itemId: string): Promise<string>;
    readJson<T = unknown>(itemId: string): Promise<T>;
    urlFor(itemId: string): string;    // signed same-origin URL for <img src>
  };
  profile: {
    get(): Promise<{ username?: string; displayName?: string; bio?: string; avatar?: string }>;
  };
  window: {
    setTitle(title: string): void;
    close(): void;
    requestFocus(): void;
  };
  onIntent(cb: (intent: { action: 'open'; itemId?: string }) => void): () => void;
};

type Item = {
  id: string;
  name: string;
  type: 'image' | 'text' | 'audio' | 'video' | 'pdf' | 'link' | 'folder' | 'app';
  mimeType?: string;
  path: string;              // "/Photos/Beaches/IMG_0001.jpg"
  fileSize?: number;
  updatedAt: number;
  caption?: string;          // from imageAnalysis
  tags?: string[];           // userTags ∪ imageAnalysis.tags
  dominantColors?: string[];
};
```

The shape of `Item` is the key product decision: we expose the *semantic*
fields (`caption`, `tags`, `dominantColors`) because that's what makes apps
feel smart. A gallery app using `item.caption` to label photos is the whole
reason this exists.

We deliberately do **not** expose `r2Key` or any signed URL the app could
exfiltrate. `urlFor(itemId)` returns a same-origin path like
`/_eternal/fs/read/:id` that only works inside this app's Dynamic Worker.

### What `/_eternal/*` looks like inside the Dynamic Worker

```ts
// runtime/index.js shipped by the platform alongside user assets
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    if (url.pathname === '/_eternal/fs/list') {
      const results = await env.ETERNAL.list({
        path: url.searchParams.get('path') ?? undefined,
        mimeType: url.searchParams.get('mimeType') ?? undefined,
        limit: clamp(Number(url.searchParams.get('limit') ?? 100), 1, 500),
      });
      return Response.json(results);
    }
    if (url.pathname.startsWith('/_eternal/fs/read/')) {
      const id = url.pathname.slice('/_eternal/fs/read/'.length);
      return env.ETERNAL.read(id);       // returns a Response
    }
    // fall through to user-authored static asset server
    return serveAsset(url.pathname, USER_ASSETS);
  }
}
```

### `EternalService` in the parent Worker

```ts
export class EternalService extends WorkerEntrypoint<Env> {
  async list(opts: ListOpts) {
    const { uid, granted } = this.ctx.props;
    const stub = this.env.USER_DESKTOP.get(this.env.USER_DESKTOP.idFromName(uid));
    const snap = await (await stub.fetch(new Request('http://internal/items'))).json<{ items: DesktopItem[] }>();
    const items = new Map(snap.items.map(i => [i.id, i]));
    const results: Item[] = [];
    for (const item of snap.items) {
      if (item.isTrashed) continue;
      const path = buildItemPath(item.id, items);
      if (!canReadItem(granted, path, item.mimeType)) continue;
      if (opts.path && !path.startsWith(opts.path)) continue;
      if (opts.mimeType && !mimeMatches(item.mimeType, opts.mimeType)) continue;
      results.push(toClientItem(item, path));
      if (results.length >= (opts.limit ?? 100)) break;
    }
    return results;
  }

  async read(itemId: string): Promise<Response> {
    // mirror of apps.ts handleAppFsRead, but sourced from ctx.props and
    // without needing a capability token
  }
}
```

We keep *one* `canReadItem()` function and share it with the existing
[apps.ts](../packages/worker/src/routes/apps.ts) capability-gated endpoints.
Single source of truth for policy.

## App manifest v1.5 (minimum viable)

We don't need the full manifest v2 from [01-apps-interop.md](01-apps-interop.md)
to ship Phase A. We need exactly enough to store grants and replay them into
`ctx.props`.

Additions to the existing `AppManifest`:

```ts
interface AppManifest {
  name: string;
  description?: string;
  version: string;
  windowConfig: AppWindowConfig;
  appId: string;
  // NEW
  permissions?: {
    fs?: { read?: string[]; mimeTypes?: string[] };
    profile?: { read?: Array<'username' | 'displayName' | 'bio' | 'avatar'> };
  };
}
```

And on the `DesktopItem` for an installed app:

```ts
interface DesktopItem {
  // …
  appManifest?: AppManifest;
  grantedPermissions?: AppGrantedPermissions;  // what the user approved
  permissionGrantedAt?: number;
}
```

`AppGrantedPermissions` already exists in [jwt.ts](../packages/worker/src/utils/jwt.ts)
— we reuse it. The load-time path becomes:

```ts
// in parent Worker /api/apps/:appId/* dispatch
const item = await userDesktopStub.getAppItem(appId);
const granted = item?.grantedPermissions ?? {};
const worker = env.LOADER.get(`app-${appId}@v${version}-${hashGrants(granted)}`, () => ({
  mainModule, modules,
  globalOutbound: null,                       // stays null until Phase C
  bindings: {
    ETERNAL: ctx.exports.EternalService({ props: { uid, appId, granted } }),
  },
}));
```

Hashing the grants into the worker ID means revocation re-keys the isolate
cache for free — no manual flush.

Apps created before this milestone have no `grantedPermissions`. They run with
an empty grants object, which is identical to today's hermetic behavior. No
migration required.

## Orchestrator changes

Four changes, smallest to largest.

### 1. Feed the LLM a desktop summary for every `app-build` turn

Right now `buildAppFromPrompt` calls a separate Workers AI model with only the
user's natural-language request. It has no idea what's on the desktop. For
desktop-aware apps that's the single biggest blocker.

```ts
async function buildAppFromPromptWithContext(ctx, prompt) {
  const stub = getUserDesktopStub(ctx);
  const snap = await loadSnapshot(stub);
  const summary = summarizeDesktopForLLM(snap);  // see §summary shape below
  return generateAppFromPrompt(ctx.env, prompt, { desktopSummary: summary });
}
```

**Summary shape.** Not the full item list (too big, PII-y). Just:

```ts
{
  counts: { image: 47, audio: 8, text: 12, pdf: 3 },
  topFolders: [
    { path: '/Photos', kindCounts: { image: 42 }, sampleCaptions: ['Sunset over Big Sur', 'Jules at the park'] },
    { path: '/Music', kindCounts: { audio: 8 } },
    { path: '/Notes', kindCounts: { text: 10 } },
  ],
  analyzedImages: 44,   // with captions/tags
  tagCloud: ['beach', 'dog', 'receipt', 'screenshot'],   // top 15
  hasPhotos: true,
  hasAudio: true,
  hasNotes: true,
}
```

The LLM uses this to (a) pick sensible defaults — "a gallery app should
default to listing `/**` with `mimeType: 'image/*'`" — and (b) generate
*believable* placeholder content that matches the real data.

### 2. Add permission declarations to generation

Extend the generation schema:

```ts
const generatedAppSchema = z.object({
  name: z.string().min(1).max(80),
  description: z.string().max(500).default(''),
  width: z.number().int().min(360).max(1600).default(720),
  height: z.number().int().min(320).max(1200).default(560),
  files: z.record(z.string()),
  // NEW — LLM declares what permissions this app needs
  permissions: z.object({
    fs: z.object({
      read: z.array(z.string()).optional(),        // globs
      mimeTypes: z.array(z.string()).optional(),   // 'image/*'
    }).optional(),
    profile: z.object({
      read: z.array(z.enum(['username','displayName','bio','avatar'])).optional(),
    }).optional(),
  }).default({}),
  rationale: z.string().max(500).optional(),       // shown in install dialog
});
```

The system prompt teaches the LLM that if its app uses `window.eternal.fs.*`,
it **must** declare the scope. If it declares `read: ['**']` it must justify
why in `rationale` — the install dialog will highlight that scope as sensitive.

### 3. System prompt: teach the API, not just the sandbox

Replace [APP_BUILD_PROMPT in OrchestratorAgent.ts:77](../packages/worker/src/agents/OrchestratorAgent.ts)
with one that:

- Shows the `window.eternal` surface as an API reference block.
- Includes 2–3 tiny worked examples: a gallery loop, a text-file reader, a
  profile-aware greeting.
- Sets the norm: prefer `window.eternal.fs.list({ mimeType: 'image/*' })`
  over asking the user to paste URLs.
- Keeps the "no external CDNs, bundle-local assets" rules that already work.
- Says explicitly: if the app doesn't need desktop data, declare zero
  permissions. Don't ask for what you won't use.

Skeleton:

```
Mode: App builder — desktop-aware

You build desktop apps that run in a sandboxed iframe on the user's EternalOS
desktop. Apps are complete static HTML/CSS/JS bundles.

Runtime APIs available to the app:
  window.eternal.fs.list({ path?, mimeType?, limit? }) → Item[]
  window.eternal.fs.read(itemId) → Blob
  window.eternal.fs.readText(itemId) → string
  window.eternal.fs.urlFor(itemId) → same-origin URL safe to use in <img src>
  window.eternal.profile.get() → { username?, displayName?, bio?, avatar? }

You must declare exactly the permissions your app uses:
  permissions.fs.read        — path globs: ['**'], ['/Photos/**'], ['/Notes/*.md']
  permissions.fs.mimeTypes   — ['image/*'], ['audio/*'], ['text/*']
  permissions.profile.read   — ['username'] is usually enough to personalize

Do not request '**' unless you genuinely need the whole desktop. Prefer
mimeType scopes over path scopes when possible (more intuitive for the user).

Desktop summary (use to make good defaults and believable placeholders):
  {{desktopSummary}}

Example — image gallery:
  permissions: { fs: { mimeTypes: ['image/*'] } }
  <img id="tpl" hidden>
  const items = await window.eternal.fs.list({ mimeType: 'image/*', limit: 200 });
  for (const item of items) {
    const img = tpl.cloneNode(); img.src = window.eternal.fs.urlFor(item.id);
    img.alt = item.caption ?? item.name;
    grid.appendChild(img);
  }

Keep the app polished, self-contained, and fast. No external CDNs.
```

### 4. Surface the permission decision to the user

The LLM declares; the user approves. A one-time dialog right after creation:

```
┌─ New app: Photo Grid ────────────────────────────────┐
│ A gallery that shows your uploaded photos,           │
│ grouped by folder.                                   │
│                                                      │
│ This app wants to:                                   │
│   ✓ Read image files on your desktop (image/*)       │
│   ✓ See your display name                            │
│                                                      │
│ Why: "Display your photos and greet you by name."    │
│                                                      │
│ [ Deny ]  [ Install & Open ]                         │
└──────────────────────────────────────────────────────┘
```

Denying installs the app with `grantedPermissions = {}`. It'll render empty
state messages from `window.eternal.fs.list()` returning `[]`. Users can
re-grant from the desktop item's right-click menu later.

This is the only UX change needed in the frontend for Phase A.

## The generation pipeline (spec → build → validate → repair)

Today's `buildAppFromPrompt` is a single `generateObject` call with up to 3
blind retries. That fixed the transport-level failure mode where the LLM was
being asked to serialize a whole app into a tool-call argument and JSON
parsing blew up on escaped HTML (the "pomodoro failure"). A blind retry only
helps if the next roll of the dice is better though — it doesn't give the
model a reason to fix what broke.

The next iteration is a staged pipeline where every stage produces a concrete
signal the next repair pass can act on. Inspired by v0's composite model
family and standard compile-and-fix loops.

### Stages

1. **Spec pass.** Model returns a short JSON plan — no source code:
   `{ name, description, width, height, permissions, rationale, intent[],
   architecture, dataShape }`. Cheap, fast, cacheable. We can show this to
   the user as a teaser ("Building Photo Grid… will read `image/*`") while
   the build pass runs. For high-permission specs (`fs.read: ['**']`) we can
   gate on explicit user approval here.

2. **Build pass.** Model receives: spec + desktop summary + API reference +
   a starter scaffold that already imports `/app-runtime/bootstrap.js` (so
   the model can't forget it). Emits files.

3. **Static validation.** No model, pure code:
   - Every file parses (HTML, CSS, JS). Catch syntax errors before bundling.
   - Declared permissions match usage: if the app calls `window.eternal.fs.list({ mimeType: 'audio/*' })`
     but didn't declare `permissions.fs.mimeTypes: ['audio/*']`, that's an
     error. Vice versa: permissions declared but never used should warn (not
     fail — users can still grant, it's just noise).
   - All relative asset references resolve to files in the bundle.
   - Forbidden patterns in user code: `<script src="http…">`, `fetch()` to
     non-allowlisted origins, and any dynamic-code-evaluation constructs
     (string-to-code execution paths).
   - Bundle size under a cap (say 2 MB uncompressed) so a runaway model
     can't DoS R2.

4. **Bundle validation.** Call `createWorker({ files })`. If it throws (bad
   imports, module resolution failure), capture the error.

5. **Runtime smoke test.** Load the just-built Dynamic Worker with a *mock*
   `EternalService` that returns synthetic items, fetch `index.html` +
   the app's declared entry points, and verify:
   - HTTP 200 on index and referenced assets.
   - No uncaught errors in the Worker console logs.
   - If the app calls `window.eternal.fs.list()`, it handles `[]` without
     crashing (catches the empty-state case).

6. **Repair pass.** If any of 3–5 failed, feed the model:
   - The original spec + files.
   - The *specific* failure (line number, error message, which API was
     misused).
   - A minimal repair instruction: "fix just this; don't rewrite the app."

   Bounded retries (2–3 max). If still failing, surface a clear error to the
   user instead of shipping broken code.

7. **Visual QA (future / phase C).** Screenshot the running app and ask a
   VLM "does this look functional and matches the intent?". Expensive; defer.

### What this buys us

- The "mediocre app code" failure mode gets concrete error signals the repair
  model can act on, instead of the current blind retry-and-hope loop.
- A pomodoro app that compiles but has `onclick` handlers pointing to
  undefined functions now gets caught at the runtime smoke test and repaired,
  instead of shipping and breaking in the user's face.
- Apps that claim `image/*` but never call `fs.list` (or the reverse) get
  fixed before they hit install UX.
- Each stage is independently swappable: we can upgrade the build-pass model
  without touching validation; we can strengthen validation without changing
  generation.

### Model routing (later, not now)

Once the stages are in place, route independently:
- Spec pass → a cheap, fast model (Kimi, Haiku).
- Build pass → the strongest available (Claude Sonnet/Opus if configured,
  fallback Kimi).
- Repair pass → same as build, with tighter temperature.

Ship single-model-everywhere first. Split once we have telemetry on which
stage actually limits quality.

### Sequencing this against the bridge work

Two reasonable orderings. We should pick one:

- **A) Bridge first, pipeline second.** Ship Phase A as described (desktop
  summary in context, `window.eternal.*` runtime, install dialog) with the
  existing single-pass builder. Then add the pipeline. Rationale: "build me
  a gallery" currently has a 0% success rate regardless of pipeline quality,
  because the runtime doesn't exist. Fix the architectural gap first, then
  improve hit rate.

- **B) Pipeline first, bridge second.** Add staged generation + validation +
  repair to the existing hermetic path. Ship a reliable hermetic-app builder.
  Then add the bridge and reuse the same pipeline (validation learns the new
  APIs). Rationale: today's main visible failure is pomodoro-class broken
  apps, not missing-desktop-access. Fix the most-felt pain first.

Recommend **A** if the target user story is "I want a gallery of my photos,"
**B** if it's "I want the apps I generate to actually work." My read from the
conversation is that (A) is the goal — but both are right answers.

## Rework the router? (No — not this milestone.)

The regex router in [OrchestratorAgent.ts:103 classifyRoute](../packages/worker/src/agents/OrchestratorAgent.ts)
is fragile but it's not what's blocking desktop-aware apps. A request like
"make a gallery" already lands in `app-build`. The change we need is
*inside* `app-build`, not before it.

Leave the router; revisit once we're past Phase B.

One small win available now: in `classifyRoute`, when a message mentions an
existing app *by name* (we can cheaply look up `listApps()` at turn start),
bias toward `app-read` or `app-build` (update) instead of starting from
scratch.

## Curated templates are not enough; context examples are

The Todo template in [appTools.ts:56 buildTodoTemplate](../packages/worker/src/agents/tools/appTools.ts)
is ~500 lines of handcrafted app. Writing one of these for every verb
("gallery", "music player", "notes", "paint") doesn't scale.

What does scale: **snippets in the system prompt.** 10–30 lines each, showing
exactly how to talk to `window.eternal.*` for each common shape:

- List-all-images → grid with captions
- List-all-text → file list + click to open
- Read-audio → playlist player
- Read-profile → personalized greeting
- Folder-scoped browse (`/Notes` or `/Photos`)

Keep the Todo template because it's the one known-good app in the repo and
useful for smoke tests. Don't grow the template library; grow the prompt
library.

## Security checklist

- **`sandbox="allow-scripts"` on the iframe stays.** No `allow-same-origin`,
  no `allow-top-navigation`, no `allow-popups-to-escape-sandbox`. (We can add
  `allow-forms` when an app needs forms.)
- **`globalOutbound: null`** on the Dynamic Worker stays until we ship the
  network allowlist in a later milestone.
- **`ctx.props` carries grants, not the user's JWT.** The Dynamic Worker never
  sees raw auth.
- **`EternalService.read`** returns blobs with `Content-Disposition:
  attachment` by default (as today) so the iframe can't accidentally navigate
  to a PDF and escape.
- **Grants are intersected at call time**: `canReadItem(granted, path, mime)`
  is the one gate. Don't bypass it even for "trusted" methods.
- **Path traversal**: `buildItemPath` walks parents with a depth limit of 16
  (already in apps.ts). Don't regress.
- **Blob size caps**: `EternalService.read` should refuse items over N MB
  (default 50? tunable) so a hostile app can't pin memory reading a video.
- **Per-app rate limit**: cap `/_eternal/*` at some small number per second per
  app+user. A runaway app loop shouldn't DoS the parent worker.
- **Item IDs are unguessable** (already UUIDs). `fs.read` still verifies the
  item belongs to `ctx.props.uid`.

## Phased delivery

**Phase A — ship desktop-aware reads.** (This doc's scope.)

1. `EternalService` WorkerEntrypoint in parent.
2. `/_eternal/fs/list` + `/_eternal/fs/read/:id` handled inside the assembled
   Dynamic Worker.
3. Platform-provided `window.eternal` runtime script auto-injected in
   `assembleWorkerFiles`.
4. `permissions` field in the generation schema + install dialog in the
   frontend.
5. Orchestrator passes desktop summary into `buildAppFromPrompt`.
6. System prompt rewrite with API reference + 3 snippets.
7. One polished reference app built through the orchestrator end-to-end:
   **Photo Grid**. Used as the acceptance test ("build me a gallery" → runs
   in one turn, shows my photos).

**Phase B — write.** `fs.write`, `fs.patch`, `fs.delete`. Requires a "write"
permission category and UX for the destructive cases (delete in particular).
`Notes Studio` as the reference app.

**Phase C — IPC + network allowlist.** The other legs of
[01-apps-interop.md](01-apps-interop.md). `Music Player` + `Visualizer` pair
as the reference duo.

**Phase D — bazaar apps.** Published apps, per-user re-bundle, trust tiers.
Out of scope here.

## Acceptance tests for Phase A

1. "Build me a gallery app for my photos." → app appears on desktop, opens,
   shows all image items with captions; permissions dialog shown at install
   time and listed `image/*`.
2. "Build a music player for my audio files." → audio items shown, click to
   play; dialog listed `audio/*`.
3. "Build a notes index." → text items listed with previews; dialog listed
   `text/*`.
4. "Build a pomodoro timer." → no permissions requested, no dialog, runs
   immediately. (No-desktop-data-needed path still works.)
5. Denying install → app installs, opens, shows a graceful empty state. User
   can grant later from right-click → App permissions.
6. Existing todo template & any previously-created apps → run unchanged.
7. Hostile test: malformed `mimeType` query param, item IDs with traversal
   characters, oversized list requests → all rejected with 4xx, not 5xx.

## Open questions

1. **Where does `app-runtime/bootstrap.js` live?** Bundled into every Dynamic
   Worker by `assembleWorkerFiles`, or served from a shared well-known path?
   Bundled is simpler and versioned per-app; shared is smaller. I lean
   *bundled* for Phase A — one source of truth, no versioning gymnastics.
2. **Do we show the install dialog for orchestrator-authored apps at all?** A
   user who asks for a gallery implicitly consents to the gallery seeing
   images. Counter: they may have meant "a gallery of cat pictures from the
   internet" and not realize it'll see `/Finance/scans`. Default to showing
   the dialog; add a "don't ask again for image-only apps I create myself"
   escape hatch later.
3. **Should `window.eternal.fs.list` ever return blobs inline?** Probably not
   — apps should fetch blobs on demand. But a batch-thumbnail API would be
   nice if gallery rendering becomes slow; defer.
4. **Should the plan pass be user-visible?** ("Here's what I'm about to
   build — approve?") Useful for high-permission apps; annoying for trivial
   ones. Tie to `rationale`: if the LLM requests `read: ['**']` we always
   show the plan for approval.
5. **Quota for app-generated writes.** When Phase B lands, app writes count
   against the user's storage quota. Need a "this app will use X bytes"
   prompt when the app grows quickly. Out of scope here; note for Phase B.
